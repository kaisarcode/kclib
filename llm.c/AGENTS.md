# AGENTS.md

## Project Context

`llm.c` is a local-first C library and CLI for generative inference with a
caller-supplied GGUF model through an external llama.cpp checkout.

It keeps expensive model and KV state resident, streams generated bytes,
supports model chat templates, LoRA, optional multimodal input, MTP, explicit
GPU offload, inspection, and local control.

It is not a hosted AI platform, agent framework, model marketplace, or
multiuser inference service.

Read `README.md` before modifying the project.

## Core Invariants

- Models, adapters, projectors, images, and KV snapshots are local files.
- No network service, account, subscription, or telemetry is required.
- One context owns its model runtime, sampling state, KV state, and errors.
- Options strings and repeated arrays are deep-copied on open.
- Generation output is streamed synchronously through a caller callback.
- Callback cancellation and context stop terminate generation cleanly.
- Chat templating is attempted and raw content remains the fallback.
- Roles remain explicit: `system`, `user`, or `assistant`.
- KV state persists across resident requests unless cleared or replaced.
- Inspection never performs output generation.
- Model-only inspection does not create a generation runtime.
- LoRA and image attachments remain bounded at 16 each.
- CPU operation remains valid; GPU and MTP are explicit optional accelerations.
- The CLI calls the public C API directly (`kc_llm_open`, `kc_llm_generate_role`,
  `kc_llm_info_query`, `kc_llm_close`); there is no in-process JSON runner.
- stdout carries generated or inspected data; diagnostics go to stderr.

## Local Inference Boundary

Do not add cloud APIs, model downloads, hosted fallbacks, usage reporting,
remote authentication, billing, user accounts, model registries, or hidden
network access.

Do not turn the library into an agent runtime. Tool calling, memory databases,
RAG, prompt catalogs, workflows, autonomous loops, and application policy
belong in separate composable tools.

## Composition

Composition happens at explicit operating-system boundaries: stdin and stdout
with the `--until` delimiter byte, stderr diagnostics, and local files for
models, adapters, projectors, images, and KV snapshots. The library uses direct
output callbacks. There is no in-process JSON runner and no network endpoint;
the CLI is a thin adapter that calls the public `kc_llm_*` API directly and
formats results to stdout.

## Architecture

The external llama.cpp checkout provides model loading, tokenization, context,
sampling, decoding, LoRA, multimodal, and optional acceleration primitives.
`libllm` owns their lifecycle and presents a stable project API.

The CLI parses configuration and reads byte-delimited requests, streams
responses through a callback, and preserves the runtime until EOF or explicit
stop.

## Context Forms

`kc_llm_open_model()` loads metadata and vocabulary for static inspection
without generation state. `kc_llm_open()` creates the full runtime.

The full context owns model, generation context, sampler, optional draft model,
multimodal projector, adapters, copied options, KV occupancy, inspection
strings, callbacks, and errors.

## Request Preparation

Generation accepts user content or an explicit role. The model chat template is
applied when available; otherwise raw content is used. Thinking configuration,
special tokens, multimodal attachments, and tokenization are part of the same
preparation path used by input-dependent inspection.

Generated bytes are delivered synchronously to the caller callback. Nonzero
callback return requests early stop.

## State and KV Memory

Resident requests share model and KV state. `kc_llm_memory_clear()` resets
conversation state. KV load/save explicitly imports or exports local snapshots.

Context inspection distinguishes current occupancy, effective capacity, model
maximum, free capacity, and projected occupancy after input. Projection excludes
future generated output.

## Sampling and Acceleration

Sampling options are explicit and mutable where control commands allow. CPU is
always a valid target. GPU layers, flash attention, LoRA, MTP draft decoding,
and multimodal projection are opt-in local mechanisms with explicit files and
limits.

No remote accelerator or managed inference fallback exists.

## Inspection

Static fields describe model metadata. Input fields require a request and use
the inference preparation path without decoding output. Unavailable values use
`KC_LLM_INFO_VALUE_NONE`; strings remain context-owned.

## Dependencies and Portability

The llama.cpp source location is explicit through `KC_LLAMACPP_DIR`; no default
checkout or download is assumed. CUDA is opt-in. Native and cross builds expose
their artifacts and target assumptions directly.

Build outputs are kept separate by kind. `bin/{arch}/{platform}/` receives only
project artifacts (`llm`/`llm.exe`, `libllm.a`, and the project shared library).
The published `libllm.a` is a complete standalone archive: at build time its
members are merged from the llama.cpp static libraries (in link order), so a
caller that links only `libllm.a` gets the full library without also linking
llama.cpp libraries. The shared library and CLI are self-contained the same way.
The standalone llama.cpp libraries and objects stay under `.build/` and are used
only to build and link; they are not published separately.

## Non-Goals

The project does not provide hosted APIs, OpenAI protocol compatibility,
multi-tenancy, accounts, authorization, billing, telemetry, model distribution,
RAG, vector storage, agent orchestration, tool execution, prompt management,
distributed scheduling, or fleet administration.

## Change Criteria

A change must solve a concrete local inference need, preserve explicit model and
state ownership, keep CPU and failure behavior legible, bound adapters/images/
control input, maintain exact inspection semantics, and avoid hidden network or
managed infrastructure.

## Core Invariants

Preserve clear separation between model-only contexts and full runtimes.
Generation, MTP, multimodal projection, LoRA, sampling, and KV operations must
fail legibly when required state is unavailable.

KV save/load and `CLEAR` are explicit operator actions. Do not add automatic
cloud persistence, conversation databases, or hidden recovery state.

Inspection accounting must use the same request preparation, role, template,
thinking, special-token, and tokenization path as inference.

## Public API and Ownership

Treat `src/libllm.h` as a compatibility boundary. Preserve deep-copy behavior,
context-owned inspection strings, borrowed callback bytes, explicit output
callbacks, and context-owned error text.

Do not expose llama.cpp internals as the public contract unless a concrete
local caller requires it.

## Source Layout

Preserve exactly:

- `src/llm.c` for the CLI;
- `src/libllm.c` for all reusable behavior;
- `src/libllm.h` for the public contract;
- `src/test.c` for all tests.

Do not create additional source, header, backend, control, multimodal, MTP, or
test files. Extend these four files. The external llama.cpp checkout remains an
explicit dependency, not source copied into `src/`.

## Forbidden Default Recommendations

Do not add hosted inference, OpenAI-compatible servers, REST APIs, accounts,
API keys, OAuth, quotas, billing, telemetry, analytics, prompt tracking, vector
databases, RAG, agent tools, job queues, distributed workers, Kubernetes,
automatic model downloads, model catalogs, or plugin systems.

Do not justify changes through enterprise serving, benchmark marketing,
multiuser scale, or AI product conventions.

## Change Evaluation

Identify the concrete local model and operation. Check model compatibility,
context and KV accounting, ownership, cancellation, CPU behavior, optional GPU
behavior, output byte streaming, state cleanup, and control command effects.

Prefer direct llama.cpp integration over another abstraction layer. Keep memory
and device choices explicit and operator-controlled.

## Resource and Security Model

Models and contexts can consume substantial bounded-by-configuration memory.
GPU offload, context size, prediction length, threads, MTP, images, and adapters
must remain explicit. Do not hide resource expansion or start background work.

The control file paths and local files carry operator authority. Validate
parsing, paths, bounds, malformed commands, snapshot compatibility, and cleanup.
Do not claim sandboxing of models, images, templates, or local file content.

## Testing

Keep every test in `src/test.c`. Cover options, ownership, model-only and full
open, static and input inspection, generation and roles, stop, KV clear/save/
load, LoRA bounds, image bounds, MTP configuration, context accounting,
malformed inputs, and cleanup. Tests exercise the public API only; model-dependent
tests must use explicit local fixtures and skip truthfully when absent.

## Build and Completion

For documentation-only changes run `kcs AGENTS.md`. For behavior
changes use repository build/tests without cleaning artifacts unless authorized.

A change is complete only when local ownership, state, resource controls,
public behavior, and documentation agree and no hosted or enterprise platform
was introduced.

The goal is direct local model inference under operator control.
